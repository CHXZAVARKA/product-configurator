Проверено 11 сентября 2026 по `codebase-design` и `DEEPENING.md`. Исходная версия: `VarioDerevoteka/krasivoe_steklo`, `origin/main`, **9f9f36476e84405e883c932d4f91f49ec4abd719**. Отдельный checkout: `/Users/owner/Documents/projects/.worktrees/krasivoe-steklo/design-audit`. Файлы ниже относятся к этой версии.

## Вывод

В редакторе есть полезная реализация 2D-оформления, масок W/V и 3D-просмотра. Для прототипа можно использовать эти возможности, предварительно отделив состояние документа от страницы. Переносить приложение целиком как готовую модульную основу рано: серверное сохранение пока не выполняет принятый контракт версий и совместной работы, а файлы изображений не имеют надёжного хранения.

Это оценка исходников и локальных проверок, не подтверждение пригодности файлов для конкретного принтера. Код исходного репозитория не изменялся, удалённых записей и публикации не было. Наш предыдущий локальный коммит истории `c0ac70a` не входит в эту upstream-версию.

## Проблемы, влияющие на наш сценарий

### 1. Загруженное изображение не становится сохраняемым ресурсом

`app/page.tsx:578` и `:755` создают `blob:` URL. В `saveProjectToServer`, `:1203`, `document` отправляется без преобразования таких ссылок в постоянные ресурсы. `renderProjectDocument` (`lib/studio/projects.ts:267`) сохраняет сведённый PNG для просмотра, но не заменяет источники редактируемых слоёв. При открытии `app/page.tsx:667` подавляет ошибки загрузки источников.

Следствие из кода: клиентская картинка может отображаться, тогда как исходные загруженные слои недоступны в другой браузерной сессии. Локальный тест подтвердил, что путь сохранения принимает и возвращает `blob:` ссылку без изменения. Это проверка сохранённых данных, не браузерный тест между двумя устройствами.

Нужен модуль ресурсов: сохранить байты исходника, получить стабильный идентификатор, затем сохранить документ с этим идентификатором. Жизненный цикл браузерных URL должен остаться внутри реализации загрузки и отображения.

### 2. Сохранение не создаёт новую версию

`lib/server/project-store.ts:41` перезаписывает `<slug>.json`. `SavedProject.version: 1` в `lib/studio/project-store.ts:17` описывает формат данных, а не историю проекта. Нет сохранённых ревизий и подтверждения конкретной ревизии клиентом.

Локальный тест двух сохранений обнаружил только последний документ и его метаданные. Это расходится с принятым требованием сохранить предыдущий вариант и согласовывать новый по прежней ссылке.

### 3. Одновременные сохранения конфликтуют

`lib/server/project-store.ts:45` формирует временное имя только из slug и PID. Два сохранения в одном процессе используют один файл. В проверке из шести параллельных записей пять завершились `ENOENT` на `rename`.

Случайное имя временного файла устранит эту конкретную коллизию, но для совместной работы также нужен явный контракт конкурентного изменения: сохранение относительно ожидаемой ревизии с возвратом конфликта, а не незаметная перезапись чужой работы.

### 4. Формат документа фактически не проверяется

`app/api/projects/[slug]/route.ts:48` проверяет внешние поля и наличие `document`/`share`. Локальный запрос с `document.layers` в виде строки и числовым `share.artwork` получил 200. Клиентский код приводит полученные данные к типам через `as`.

Проверка формы, идентификаторов слоёв, числовых преобразований, ссылок на ресурсы и назначений W/V должна происходить при чтении/сохранении документа. Некорректные состояния нельзя отдавать холсту и 3D как будто они уже проверены.

### 5. 3D-просмотр и печатный результат имеют разные правила

`draw` и `drawMask` учитывают видимость по умолчанию, так работают 3D и клиентский просмотр. Но `exportCmykTiff` (`lib/studio/export-tiff.ts:254`) передаёт `respectVisibility=false` в цвет и маски. Скрытые слои включаются в сведённые каналы печати. README описывает сохранение выключенных слоёв при экспорте, поэтому это отмечено как неоднозначный контракт: сохранение редактируемого скрытого слоя и включение его в печатную композицию должны быть разными решениями.

`exportLayeredPsd` получает только слои, без whiteIds/varnishIds. Его нельзя считать эквивалентом TIFF-пакета с плашечными каналами. `rgbToCmyk` в TIFF выполняет арифметическое преобразование, ICC-профиля в записываемом наборе TIFF-тегов нет. Проверка TIFF ограничена заголовком; проверка PSD ограничена структурой, а не пикселями и технологическими каналами.

До использования для производства нужны эталонные файлы и проверка полного цикла экспорта/импорта: видимость, прозрачность, маски, размеры, плашечные каналы и соответствие процесса реальной печати. Проверка в Photoshop/на принтере в этом аудите не выполнялась.

### 6. Доступ пока соответствует общей публичной витрине

GET списка и полного документа открыт без ключа; ключ регулирует запись. Это подтверждено локальным GET при настроенном ключе публикации. `app/[project]/page.tsx` также предлагает список проектов при неизвестном slug. В конфигурации без ключа сервер разрешает запись; установлен ли ключ на production, этот аудит не проверял.

Для клиентских проектов нужно отдельно определить чтение по ссылке, право редактирования и подтверждение версии. Не переносить нынешний общий ключ как готовую модель доступа для клиента и сотрудника.

## Оценка модулей по depth и locality

### Документ оформления

Сейчас его interface распределён между `Layer`, глобальным `images`, `whiteIds`, `varnishIds`, `revision`, множеством setters и логикой истории в `app/page.tsx`. Вызывающий код обязан знать порядок загрузки изображений, обновления счётчика и восстановления отдельных полей. Это увеличивает interface без дополнительного leverage.

Предлагаемый модуль документа принимает команды редактирования и отдаёт снимок. Он владеет идентификаторами, слоями, назначениями масок, undo/redo и проверкой допустимости изменений. Загрузка байтов и создание DOM-элементов остаются за внутренним seam. Его interface проверяется через пользовательские операции, например «удалить слой → отменить → восстановились слой и его назначения W/V».

### 3D-просмотр

У `CylinderPreview` уже есть depth: небольшой набор параметров скрывает CAD-загрузку, материалы, камеру и управление. Его не нужно переписывать только из-за размера файла. Ограничение: интерфейс привязан к размерам и деталям одного изделия, принимает изменяемые наборы и внешний счётчик `revision`, а семантического события выбора детали нет.

Новый seam: снимок сцены на входе, выбранная деталь как событие на выходе. Внутри остаются Three.js, загрузчики и геометрия «Авторского». Движение по шагам, меню и выбор детали должны проходить через один модуль сценария. Adapter лампы пока не создаём: её реализацию пользователь отложил.

### Подготовка печатного файла

Импорт TIFF уже имеет небольшой interface `ArrayBuffer → ImportedTiff`, скрывающий существенную реализацию. Нужно усилить проверку входных данных и доказать совместимость эталонами. Экспорт смешивает кодирование, создание ссылок и браузерное скачивание, что мешает проверять результат через interface.

Модуль подготовки получает снимок оформления и печатную спецификацию, возвращает файлы и результаты проверки. Adapter скачивания отдельно показывает файлы пользователю. Так один результат используется для скачивания, передачи сотруднику и проверки без кликов по браузерным ссылкам.

### Проект и ревизии

`project-store` сейчас является небольшим файловым adapter, но не модулем согласования. Логику ревизий, конкурентного сохранения, подтверждения и доступности по ссылке должен владеть отдельный глубокий модуль. Файловый adapter можно проверять реальной временной директорией, как сделано в приложенном воспроизведении. Другой backend нельзя добавлять только ради абстракции: потребность определяется требованиями и реальными ограничениями.

### Расчёт

`authorPrice` является чистым вычислением и удобен для проверки, но расположен вместе с браузерным хранилищем ссылок в `share.ts`. Его набор опций не покрывает все действующие шаги Tilda и разовые услуги. Значения и сроки здесь не сверялись заново с таблицей. Это отдельный модуль расчёта с проверенными данными «Авторского», а не готовый перенос текущей сметы.

## Порядок дальнейшей работы, предложение

1. Зафиксировать один документ оформления, ссылки на его ресурсы и одинаковое значение видимости/масок для просмотра и экспорта.
2. Отделить существующие операции оформления от страницы. Сохранить 3D-сцену и алгоритмы, которые проходят проверки.
3. Проверить варианты клиентского UI на одном сценарии «Авторского»: загрузить изображение, разместить, выбрать слой, назначить белила/лак, вернуться к комплектации через меню или 3D.
4. Для сегментации сначала определить, что именно она возвращает в документ: выделенную область, отдельный слой или маску. Реализацию выбирать после этого. На первом сравнении UI допустимость подготовленного примера остаётся решением пользователя.
5. Перед реальным совместным использованием: хранение ресурсов, неизменяемые ревизии, согласование, конфликты записи и правила доступа.

Это план использования проверяемых частей, а не утверждённая архитектура или уже выполненный рефакторинг.
