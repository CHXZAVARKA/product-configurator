# Простая 3D-физика и остановка после действий

11 сентября 2026. Краткое продолжение исследования для 36 осколков в камере глубиной 10 мм. Исследователь не изменял код. Проверены runtime и точный исходник `@dimforge/rapier3d-compat` 0.20.0; добавлены промежуточные контрольные результаты основного агента для 0.19.3. Ни одна из этих конфигураций здесь не объявляется готовой.

## 1. Минимальный вариант: Rapier, простой коллайдер, подробная картинка

Исследовать Rapier 3D с выпуклой призмой без фасок либо обычным тонким cuboid, фиксированным шагом и CCD для движущихся осколков. Начальные 120 Гц и контрольные 240 Гц требуют сравнения столкновений и CPU. Полное перемещение и переворот в 10 мм остаются настоящими. Cuboid проще задавать, но его углы могут создавать зазоры между неправильными визуальными осколками. Пятиугольная призма ближе к картинке. Динамические triangle mesh здесь не нужны; Rapier рекомендует для динамических тел выпуклые формы, а для cuboid отмечает меньшую стоимость относительно round cuboid. Скорость Rapier в этой конфигурации из документации не следует. [Rapier Colliders](https://rapier.rs/docs/user_guides/javascript/colliders/)

Самописная PBD может проектировать позиции в допустимую область, но для настоящих вращающихся пластинок всё равно потребуются контакты, ориентация, трение и проверка пролётов между шагами. 2,5D с фиксированными слоями теряет требуемый свободный переворот. Поэтому это не более простой следующий шаг для уже подключённого Rapier. [Оригинальная статья Position Based Dynamics](https://matthias-research.github.io/pages/publications/posBasedDyn.pdf)

## 2. Сантиметры и defaults: есть опасное расхождение документации с runtime

`lengthUnit` по точному исходнику npm 0.20.0 задаёт количество единиц сцены на метр: для сантиметров 100, миллиметров 1000, метров 1. Он масштабирует внутренние допуски. `npm view @dimforge/rapier3d-compat@0.20.0 gitHead` вернул `3e12c2679cb1940a876bde93af9cec0cf2f57944`; ссылки на этот commit ниже соответствуют исследуемому пакету. [Rapier, IntegrationParameters source](https://github.com/dimforge/rapier/blob/3e12c2679cb1940a876bde93af9cec0cf2f57944/src/dynamics/integration_parameters.rs)

При этом документация JS и поставляемый с 0.20.0 `integration_parameters.d.ts` описывают defaults как 0.001 и 0.002. **Реально установленный WASM 0.20.0 возвращает другие значения**. Чтение нового `RAPIER.World` в Node без симуляции показало:

```json
{"version":"0.20.0","dt":0.01666666753590107,"lengthUnit":1,
 "error":0.004999999888241291,"prediction":0.019999999552965164,
 "iterations":4,"pgs":1,"ccd":1}
```

Воспроизведение: импортировать локальный `tooling/node_modules/@dimforge/rapier3d-compat/dist/rapier.mjs`, вызвать `await RAPIER.init()`, создать `World`, прочитать `world.integrationParameters` и вызвать `world.free()`. Это проверка значений библиотеки, не тест скорости. [Документация API для сравнения](https://rapier.rs/javascript3d/classes/IntegrationParameters.html)

Физический порог равен `normalized × lengthUnit`. Поэтому смена исследованного `lengthUnit=1` на 100 без явных параметров даст **5 мм geometric slop и 20 мм prediction**, крупные значения для этой камеры. Важно: в фактическом solver 0.20.0 параметр `normalizedAllowedLinearError`, несмотря на старое описание в JS API, **не является глубиной проникновения, которую позиционный solver оставляет неисправленной**. Его новое назначение: geometric slop; подробнее в разделе 3. Пример явного масштаба параметров для эксперимента:

| Параметр | Физическая величина | Для сантиметров, lengthUnit 100 | Для метров, lengthUnit 1 |
| --- | --- | --- | --- |
| gravity | 9,81 м/с² | 981 | 9,81 |
| normalizedAllowedLinearError | 0,02 мм | 0,00002 | 0,00002 |
| normalizedPredictionDistance | 0,2 мм | 0,0002 | 0,0002 |
| dt | 1/120 с | 1/120 | 1/120 |

Это выбранные инженерные параметры для проверки, не официальные универсальные рекомендации и не обещание проникновения меньше 0,02 мм. Переход на SI рекомендован общей документацией, но для миллиметровых объектов нельзя считать его достаточным исправлением. По промежуточным опытам основного агента, tiny hull в SI вели себя хуже варианта в миллиметрах; эти опыты ещё не изолируют причину различий. [Rapier Common mistakes](https://rapier.rs/docs/user_guides/javascript/common_mistakes/)

## 3. CCD и заморозка не исправляют уже существующее пересечение

Rapier CCD учитывает перенос и вращение, ограничивает движение до контакта и имеет вычислительную цену. Увеличение `maxCcdSubsteps` помогает уменьшать потерю симулируемого времени при нескольких контактах. Оно не является обещанием устранить любую исходную коллизию или продавливание контактного решателя. [Rapier, Continuous collision detection](https://rapier.rs/docs/user_guides/javascript/rigid_bodies/#continuous-collision-detection)

Нужно сначала проверить состояние **до первого шага**: в текущем коде расстояние между начальными центрами 9 мм, а поворот вытянутого осколка может дать большее расстояние между крайними точками. После смены коллайдера начальная сетка тоже должна гарантировать отсутствие пересечений. Затем отдельные минимальные проверки: один осколок на полу; два осколка друг на друге; два движущихся навстречу с вращением; только затем 36 в камере. Это план диагностики, причина наблюдаемых пересечений пока не доказана.

### Почему изменение contact frequency не исправило пол в 0.20.0

Основной агент воспроизвёл отдельный cuboid на fixed-полу: размеры осколка 8×8×1,4 мм, стартовый центр z=9 мм, g=9,81 м/с², sleep выключен. Через 2 секунды центр z≈0,582285 мм вместо 0,7 мм, проникновение ≈0,117715 мм. Частоты контакта 30/120/1000 и шаги 120/240 Гц дали одинаковое проникновение, хотя getter ERP менялся. Это локальный минимальный опыт, не замер производительности.

Точный исходник npm 0.20.0 объясняет нечувствительность этого опыта:

- JS-setter `contact_natural_frequency` меняет **только `contact_softness.natural_frequency`**, и getter ERP тоже читает `contact_softness`. [WASM bindings, строки 19–21 и 59–61](https://github.com/dimforge/rapier/blob/3e12c2679cb1940a876bde93af9cec0cf2f57944/typescript/src/dynamics/integration_parameters.rs#L59)
- Контакт с fixed-телом выбирает **другой набор, `static_contact_softness`**. Поэтому параметры, изменённые через этот JS-setter, не влияют на данный контакт с полом. [Выбор параметров, строки 430–445](https://github.com/dimforge/rapier/blob/3e12c2679cb1940a876bde93af9cec0cf2f57944/src/dynamics/solver/contact_constraint/contact_with_twist_friction.rs#L430)
- Defaults у static softness: 60 Гц, damping 10; у dynamic: 30 Гц, damping 10. В просмотренных JS/WASM bindings setter для static softness отсутствует. [Defaults](https://github.com/dimforge/rapier/blob/3e12c2679cb1940a876bde93af9cec0cf2f57944/src/dynamics/integration_parameters.rs#L60), [список bindings](https://github.com/dimforge/rapier/blob/3e12c2679cb1940a876bde93af9cec0cf2f57944/typescript/src/dynamics/integration_parameters.rs)
- Позиционный bias использует `dist × erp_inv_dt`, без deadzone `allowed_linear_error`. Комментарий прямо различает geometric slop и solver deadzone. Поэтому уменьшение error не задаёт потолок глубины проникновения. [Строки 480–485](https://github.com/dimforge/rapier/blob/3e12c2679cb1940a876bde93af9cec0cf2f57944/src/dynamics/solver/contact_constraint/contact_with_twist_friction.rs#L480)

Таким образом, solver не игнорирует ERP вообще: опубликованный JS-setter настраивает другой контактный режим. Прежняя рекомендация продолжать повышать этот setter для fixed-пола отменена. Из исходника не следует точное значение 0,117715 мм или причина всех межтелесных пересечений, для них нужны отдельные опыты.

### Контроль 0.19.3 ещё не прошёл проверку

Основной агент сообщил промежуточный контроль Rapier 0.19.3 в миллиметрах, `lengthUnit=1000`, contact frequency 1000, 240 Гц: межтелесное проникновение после укладки 0,034–0,161 мм, в движении 0,454–0,822 мм; в отдельные моменты вершины выходили за границу примерно на 0,9 мм. Стенки и коллизии продолжают исправляться. Эти числа не доказывают готовность, пригодность 0.19.3 или превосходство версии при равных условиях: масштаб и параметры тоже различались.

Выбирать версию и движок для прототипа нужно по воспроизводимому тесту конкретной насыпки. Последняя версия npm сама по себе не является лучшей для задачи; более старая тоже не считается исправлением до прохождения проверок.

## 4. Явный цикл «действие → укладка → заморозка»

Предлагаемое управление сцены:

1. Наклон, встряхивание, изменение количества или формы будит тела через `wakeUp()`, сбрасывает окно покоя и запускает фиксированные шаги.
2. После окончания ввода тела укладываются. Окно 0,3–0,5 с подтверждает малые линейную/угловую скорости и смещения. Начальные кандидаты: скорость <0,02 см/с, угловая <0,03 рад/с, дрейф позиции <0,002 см. Дополнительно проверяются стенки и максимальное взаимное проникновение, ориентир ≤0,002 см. Эти UX-пороги надо подобрать на тесте.
3. При успешной укладке вызвать `sleep()` у всех тел, сохранить текущие позы и перестать вызывать `world.step()`. Остановить обновление текстуры насыпки. Коллайдеры сохраняются, тип тела не меняется на fixed.
4. Следующее действие снова будит тела. Поворот камеры просмотра, цвет и логотип могут требовать только перерисовки, без запуска физики, если силы и геометрия не изменились.

Rapier предоставляет `sleep()`, `isSleeping()`, `wakeUp()`; спящие тела не симулируются до пробуждения. Если весь world остановлен приложением, автоматическое пробуждение от контактов само не выполнится, поэтому запуск после действий должен быть явным. [Rapier Sleeping](https://rapier.rs/docs/user_guides/javascript/rigid_bodies/#sleeping), [RigidBody API](https://rapier.rs/javascript3d/classes/RigidBody.html)

Не замораживать по одному только таймеру и не считать сон доказательством хорошей геометрии: так можно закрепить нынешнее пересечение. Пользовательская кнопка паузы может остановить сцену немедленно, но автоматическая остановка после укладки должна пройти проверку.

## 5. Что считать готовым

После каждой новой настройки проверить: нулевые исходные пересечения; допустимую ошибку пола и стенок; максимальную глубину межтелесного проникновения во время тряски и после укладки; отсутствие застывших в воздухе осколков; неизменность поз во время freeze; движение и переворот после wake. Проверка только `escaped=0` на границах кадров недостаточна. Затем измерить CPU и FPS, никаких обещаний ускорения для этого нового варианта пока нет.

Выбранный следующий шаг: **оставить простую Rapier 3D, явно задать малые допуски, исправить начальные/контактные пересечения и добавить settle/freeze/wake**. Новая PBD или плоская симуляция сейчас увеличивает объём работы и меняет поведение, которое пользователь хотел сохранить.

## Итог реализации и проверки

Реализован вариант Rapier **0.19.3** в миллиметрах: 480 фиксированных шагов в секунду, четыре итерации, CCD, простая выпуклая оболочка каждого осколка. Отдельная проекция внутрь цилиндра устраняет кратковременный выход за тонкую стенку. Частота 120–240 Гц в испытанных настройках оставляла заметные пересечения; увеличение частоты с уменьшением числа итераций дало приемлемый результат. Это выбор для данной камеры, не рекомендация для всех проектов.

Условие заморозки проверяет изменение позы за два последовательных окна по 250 мс: менее 0,12 мм и 0,02 рад для каждого тела в течение всего окна. Одна скорость оказалась плохим признаком покоя: импульсы контактного решателя давали шум при почти неподвижных позах. После укладки весь world перестаёт шагать, наклон и встряхивание явно сбрасывают покой.

[Проверка контактов](../../prototypes/PROTOTYPE-optics/evidence/contact-check.json): три набора по 36 стёкол, тряска и наклоны, затем укладка. Все замерли; максимальное проникновение 0,26–0,48 мм в движении, 0,03–0,04 мм после укладки. Выходов за границы не зафиксировано. [Численные проверки](../../prototypes/PROTOTYPE-optics/evidence/numerical-checks.json) отдельно подтверждают отсутствие шагов после заморозки и пробуждение от обоих действий.

[CPU-замер](../../prototypes/PROTOTYPE-optics/evidence/current-performance.json): Apple M1, медиана 6,83 мс на логический кадр, p95 12,28 мс для 36 стёкол. [Браузерная проверка](../../prototypes/PROTOTYPE-optics/evidence/fast-browser-checks.json): 58 fps при первом движении с загрузкой сцены, 60 fps при повторном движении; шаги и перерисовки в покое не увеличиваются. Это локальные измерения, слабые мобильные устройства не проверены.
