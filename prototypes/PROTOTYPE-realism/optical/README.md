# Преломление одного и двух осколков

Стенд ticket02 построен от `0d51e61579e1a49aff5c4811ab2ce1b48c712ed6`. Он не меняет физику, общий просмотр или старые прототипы.

Откройте `PROTOTYPE-optical.html` прямо с диска. Это самостоятельный HTML без внешних запросов. Выберите один или два осколка, толщину и направление взгляда. Кнопка контроля накапливает 64 сэмпла на пиксель. Изменение геометрии или взгляда отменяет старый контроль. Оба изображения получают одинаковые записанные позы.

## Проверки

Из корня проекта выполните:

```sh
node prototypes/PROTOTYPE-realism/optical/evidence/check.mjs
node prototypes/PROTOTYPE-realism/optical/evidence/convergence.mjs
python3 prototypes/PROTOTYPE-realism/optical/build.py
node prototypes/PROTOTYPE-realism/optical/evidence/browser.mjs
```

Последняя команда запускает временные Chrome CDP9348 и HTTP3038 и закрывает их после проверки. Нужны установленный Google Chrome, Node с WebSocket и Python3. JSON и изображения остаются в `evidence/`.

## Геометрия и перенос света

`transport.mjs` использует наружные плоскости того же выпуклого меша, который создаёт `../geometry.mjs`. Пересечение луча задаёт точку входа и выхода. Направление меняется по Снеллиусу на каждой границе. Пропускание учитывает точный диэлектрический Френель. Цвет рассчитывается как `exp(-absorption * pathMm)`, поглощение задаётся в обратных миллиметрах.

Глаз стенда расположен при z=18 мм и смотрит по −Z. Фон расположен при z=−18 мм. Это направление соответствует CAD: glazok при z=195…208 мм, prizma при z=12…192 мм, steklo при z=192…195 мм. За диском nasipka при z=10…12 мм находится рабочая область свободных осколков при z=−0,5…10 мм, затем elving при z=−17,65371…−0,5 мм и источник с отрицательной стороны Z. Расстояние между линиями сетки равно 1 мм. IOR равен 1,5. Начальные толщины 2,4 и 2 мм, формы и коэффициенты поглощения являются временными предположениями. Они не измерены по реальному изделию.

Для центрального луча одного осколка сетка смещается на 0,354 мм. После двух осколков итоговое смещение 0,205 мм. Здесь смещения частично компенсируются из-за противоположных наклонов. Луч проходит четыре границы, длины пути 2,491 и 2,055 мм. Итоговое RGB-пропускание 0,686,0,720,0,770. При уменьшении настоящей геометрической толщины первого осколка вдвое путь становится 1,246 мм, красное пропускание увеличивается с 0,764 до 0,838. Тест направления сравнивает разные пути внутри обоих тел, а не только изменение выборки фона без стекла.

Быстрый WebGL2-проход прослеживает один передаваемый луч. Он продолжает полное внутреннее отражение по реальной нормали вместо чёрного обрыва. Если луч выходит мимо фоновой плоскости, он получает свет окружения. Внешние отражённые ветви Френеля этот режим не прослеживает. Лимит составляет два выпуклых непересекающихся тела во всей сцене, по десять плоскостей, шестнадцать границ на луч. Это не лимит двух слоёв на пиксель при произвольном количестве видимых осколков. Рендерер отвергает больше двух тел и IOR, отличный от 1,5. Для полной насыпки нужен отдельный алгоритм выбора слоёв в ticket05.

Контроль представляет собой CPU Monte Carlo трассировку через ту же геометрию. На каждом интерфейсе отражение или пропускание выбирается с вероятностью Френеля. Лучи получают свет от светящейся плоскости сетки и площадного источника в окружении. Граница источника задаётся конусом направлений с `dot >0.94`, направление `normalize([-0.4,0.5,-1])`, RGB-яркость 3,2.9,2.7. Остальное окружение имеет яркость 0.14,0.18,0.24. Контроль учитывает повторные внутренние и внешние отражения. Глубина 24, seed20260914, jitter внутри пикселя, без фильтра шумов. Это настоящий геометрический контроль, но не проверка сходства с реальным образцом.

64spp сохраняют шум на кромках. `convergence.json` сравнивает 8192 и 16384 лучей в трёх фиксированных точках, максимальное изменение среднего около 0,00053. Такой замер не доказывает сходимость всего изображения или выбранной глубины. Ни один режим не включает шероховатость, дисперсию, объёмное рассеяние или проверенные каустики на отдельном принимающем экране. Модель предполагает непересекающиеся стеклянные объёмы в воздухе.

## Подключение к общему просмотру

```js
import {solidFromChip, transmittedRay, intersectSolid, nearestInterface}
  from './optical/transport.mjs';

const solids=chips.map((chip,i)=>solidFromChip(chip,poses[i],absorption[i],1.5));
// ray приходит со стороны +Z и смотрит к −Z.
const throughGlass=transmittedRay(ray.origin,ray.direction,solids,{backgroundZ:-36});
// Выходящий луч после осколков передаётся в CAD эльвинга.
const throughCAD=cadSolid.trace(throughGlass.ray);
const combinedWeight=throughGlass.weight.map((v,i)=>v*throughCAD.transmittance[i]);
// Фон z=−36 выбирается по throughCAD.ray.origin и throughCAD.ray.direction.
// throughGlass.point до CAD не используется как итоговая выборка фона.
```

Порядок прямого луча составляет осколки, CAD эльвинга, затем отрицательный Z-фон. Пример предполагает проверенные непересекающиеся позы и успешные выходящие лучи обоих модулей. Если поверхности конкурируют по порядку пересечения, нужен общий выбор ближайшего интерфейса. Полная обработка отражённых путей, которые возвращаются из CAD в осколки, требует общего обхода интерфейсов в ticket05. Кэш CAD должен учитывать входящий преломлённый луч: после движения осколков прежние входящие направления могут стать неверными.

`transmittedRay` и `traceSample` принимают явный `backgroundZ` и работают в обоих направлениях. Направление −Z и отдельный положительный Z-вариант проверяются в `checks.json`. Отрицательный фон является только текущим значением по умолчанию стенда.

`solidFromChip` принимает `vertices`, `indices`, `id` и позу `{positionMm:[x,y,z],rotation:[x,y,z,w]}` в миллиметрах CAD. Нормали треугольников должны смотреть наружу, тело должно быть выпуклым. `intersectSolid` и `nearestInterface` не ограничивают число тел и доступны для собственного выбора ближайших границ в ticket05. `transmittedRay` по умолчанию ограничен 16 границами, параметр `maxInterfaces` задаёт другой лимит. При уходе в окружение `point=null`, `status='environment'`, `ray` и `weight` сохранены. При исчерпании лимита вес становится нулём. Возврат `lengths` позволяет показывать фактические пути отдельно по каждому телу.

## Измерение стоимости

`browser.json` содержит текущий замер 120 кадров 256×256 с `gl.finish`, то есть с ожиданием завершения GPU. Использован Apple M1 через ANGLE Metal. p95 около 0,1 мс находится на границе разрешения CPU-часов, это не точная оценка стоимости GPU. Замер не включает дисплей, физику или остальной интерфейс. Он не доказывает бюджет полной насыпки. Неподвижный CPU-контроль занимает примерно 8 секунд для одного тела и 15 секунд для двух. Точное время каждого сохранённого кадра находится рядом с его позами в JSON.

`layers-1-64spp.png` и `layers-2-64spp.png` показывают оба режима рядом. Отдельные `fast-*.png` и `control-*-64spp.png` имеют исходное разрешение 256×256. Browser-проверка дополнительно сравнивает реальные WebGL-пиксели с независимыми CPU-лучами и проверяет отсутствие WebGL и сетевых ошибок.
